###### Version Control
- Management of changes to documents, programs, web sites
- **GIT**:
	- Git - is command line client software that supports access to both local and remote repositories.  
	- GitHub - is a Web-based Git repository hosting service.  
	- Repo – Acronym for a repository – A set of files that are grouped together as a project.
- **Git – Key Commands**
	- **Init** – Creates a Git repo.
	- **Add** – Adds files to the staging area.
	- **Commit** – The act of adding source code changes to the repo. Takes a snapshot and commits it to the history.
	- **Clone** – Clones a repo into a new directory. Useful for starting a new branch from a remote repo.
	- **Checkout** – Switches branches, allows selection of an old commit or file revision.
	- **Merge** – Merges changes back to the main branch.
	- **Push** – Sends a series of commits to move a local branch to another repository.
	- **Fetch** – Downloads a branch, but doesn’t integrate. Allows manual inspection before merge.
	- **Pull** – Automated version of fetch, downloads a branch, and attempts merge.

###### Test to Pass and Test to Fail
- **Confirmation of Expected Operation**  
  - **Test to Pass**  
  - These are considered the normal data sets.  
  - Use cases (supplied during specification development) are useful to develop meaningful test data sets.

- **Confirmation of Expected Error Conditions**  
  - **Test to Fail**  
  - These are considered to be non-normal data sets.  
  - Out of range data sets, invalid data should result in continued program operation using a standard error handling mechanism.
###### Handout: Develop Test Cases
```java
public static ArrayList<Integer> calculateGradeMode (ArrayList<Integer> allGrades){  
	final int NUMGRADES = 101;  
	
	int [] frequency = new int[NUMGRADES];  
	for (int grade : allGrades)  
	if (grade >= 0 && grade < NUMGRADES)  
		frequency[grade]++;  
	else  
		throw new IllegalArgumentException("Invalid grade in input : " + grade + " All grades must be between 0 and 100");  
		
	int minimumModeFrequency = 2; 
	
	ArrayList<Integer> mode = new ArrayList<Integer>();  
	for (int grade=0;grade < NUMGRADES; grade++)  
	{  
		if (frequency[grade] > minimumModeFrequency)  
		{  
			minimumModeFrequency = frequency[grade];  
			mode.clear();  
			mode.add(grade);  
		}  
		else if (frequency[grade] == minimumModeFrequency)  
			mode.add(grade);  
	}  
	return mode;  
}
```

###### Exploratory Testing / Black Box Testing
- Testing that is done where access to the program source code is not available
###### Black Box Test Case Parts
- Each test case requires:
	- Data input
	- Reason for test
	- Expected output 
	- Actual output
	- Compare expected with actual 
		- successful 
		- not successful 
###### Test to Pass
- Normal data that the program should accept AND produce correct output
###### Test to Fail
- Not normal data that the program should NOT accept BUT still handle the errors elegantly 
- For example a test to fail test case that does not produce an error message when required would be Not Successful
###### Boundary Testing
- It is not feasible to test every single input value – complete data coverage
- Given a single input, which has a valid range of 1 to 10
	Test to Pass – Valid Partition
	- 1 (lower bound)
	- 10 (upper bound)
	- 5 (a value from the middle of the partition)
	
	Test to Fail – Invalid Partition
	- 0 (1 below lower bound)
	- 11 (1 above upper bound)

###### Bug Reporting and Resolution

- **When to Report Bugs**: 
  - Bugs should be reported as soon as they are identified. Effective bug reporting is crucial for ensuring timely resolutions. A clear description and a documented procedure to reproduce the bug (including video if possible) increases the likelihood of fixing the issue.
  - Useful tool: [UserTesting](http://www.usertesting.com/) for video recordings.

- **Attributes for an Effective Bug Description**:
  - Provide key information such as the operating system version, software build, and any specific conditions.
  - **One bug per report**: Reporting multiple bugs in one ticket can lead to confusion. If bugs are related, reference the other ticket but avoid bundling them together.
  - Include a simple, step-by-step procedure to reproduce the bug, ensuring it's easy for developers to verify.

- **Bug Report Content (Tester Perspective)**:
  - Essential information includes program identification, version information, and date of report.
  - Include details such as:
    - **Reported by**: Who discovered the bug.
    - **Bug type**: (Coding, Design, UI, Documentation)
    - **Problem summary**: Reproducibility (Yes/No), steps to reproduce, and suggestions for a fix.

- **Bug Report Content (Developer Perspective)**:
  - Developers should track the bug status, priority, and resolution. Key points include:
    - **Assigned to**: Who is handling the fix.
    - **Status**: Open/Closed
    - **Priority**: Determines the urgency of the fix.
    - **Resolution**: (Fixed, Pending, Deferred, etc.)
    - **Resolved by with Date**: Track when the issue was addressed and fixed.
    - **Solution Tested**: Confirmation that the fix works, with version/build details.

- **Bug Workflow**:
  - Bugs pass through stages such as Open, Review, Resolved, and Closed, with potential for Deferred status if a bug is postponed for future fixes. Developers and project managers should review the bug and its resolution.

- **Responsibilities**:
  - **Programmer's Role**: The programmer must confirm if it's a bug or if it’s working as designed. If it's a bug, they either defer or resolve it.
  - **Tester's Role**: The tester confirms whether the fix works or if the bug is still present. If the bug isn't fixed, it is returned to the "Open" status.

- **Reasons for Bug Delays or Not Being Fixed**:
  - Bugs may be delayed or not fixed for reasons like time constraints, the bug not being severe, difficulty in reproducing, or the fix being too risky or not worth the effort (e.g., affecting a few users).

- **Bug Priorities**:
  - Bug priorities determine how quickly an issue is addressed. High-priority bugs get fixed immediately, while low-priority ones may be delayed. Developers often assess priority based on the bug's impact and severity.

- **Writing Bug Reports**:
  - A bug report should include:
    - **Bug identifier/number**: A unique ID for tracking.
    - **Test case number**: The test case in which the bug was found.
    - **Bug description**: Steps to reproduce, actual vs expected results, any assumptions about the cause, and screenshots if available.
  - A good bug description helps the developer resolve the issue quickly, and detailed information ensures that future reports are clear and actionable.

- **Bug Report Example**:
  - In practice, for a **black box test case** example, you might report a bug with clear steps and expected vs. actual results to ensure developers can fix the problem. Confirm the steps before submitting.

#### 8. B) Review Material

###### Identifying Threats
- Create a list of threats to the application/system
- Form a team of domain experts to analyze issues
- Identify valuable assets:
  - Financial
  - Personal Information
  - Trade secrets
- Review Authorization and Authentication
- Examine data flow (within and between systems)
- Identify weak points: potential threats

###### Ranking Threats
- Consider the following factors:
  - Damage potential (financial, personal information leaks)
  - Likelihood of attack success
  - Required expertise (novice or expert, hacking software availability)
  - Affected users (number of impacted users)
  - Discoverability (ease of uncovering the weakness)

###### Testing for Software Security
- Software security testing falls under the category "Test to Fail"
- Most vulnerable programming languages:
  - C / C++ (memory overwriting, buffer overflow)
  - HTML / Javascript / SQL (via injection through web interfaces)

###### Examples of Reducing Vulnerability
- Operating system adjustments:
  - NX-Bit (No-Execute) bit, eXecute Disable (Intel), Enhanced Virus Protection (AMD), XN (ARM)
  - Firewalls protect against port scanning
- Modern programming languages:
  - .NET / Java (virtual machine languages with built-in memory protection)
  - Array out-of-bounds exceptions, mandatory variable initialization

###### Website Vulnerability Scanner
- Free tools available to identify website vulnerabilities
- OWASP (Open Worldwide Application Security Project) maintains a list of tools:
  - https://owasp.org/www-community/Vulnerability_Scanning_Tools

###### Common Software Security Attacks
- Attacks fall into 4 categories:
  - Attacking Software Dependencies
  - Breaking Security Through the User Interface
  - Attacking Design
  - Attacking Implementation

###### Attacking Software Dependencies
- Applications depend on environmental components (OS, .NET, Java)
- Possible manipulation tactics:
  - Blocking access to system components
  - Manipulating access via the Windows registry
  - Forcing application to use corrupt files
  - Running in low resource conditions (memory, disk, bandwidth)

###### Attacking the User Interface
- Result: privilege escalation or unauthorized access to secret info
- Common techniques:
  - Buffer Overflow (exploitable when input length is not constrained)
  - Examining common switches and options for security flaws
  - Exploring escape characters and commands that cause unintended behavior

###### Attacking Design
- Design flaws can lead to security vulnerabilities:
  - Special/default accounts (e.g., Master Key)
  - Test modes left enabled after deployment
  - Port scanning to identify open TCP/IP ports
  - Repetitive command execution (Denial of Service)
  - Testing default values (uninitialized variables)

###### Attacking Implementation
- Focus on how the system is implemented:
  - Exploiting time between check and use of data
  - Malicious DLL replacement
  - Exposing details through error messages

###### Protecting System Access
- Real-world examples of system access breaches:
  - Adobe (2013) - cryptographic blunder
  - Sony (2014) - top-secret password lists
  - Facebook (2019) - storing passwords in plain text
- Lessons learned?

###### Testing Account / Password Strength
- Special accounts must be eliminated before release
- Password strength control:
  - Minimum length (8-10 characters), required character types
  - Use hashed passwords (not encrypted) and re-compute hashes on entry
- Improve password hashing:
  - Add SALT to passwords, unique for each user
  - Use multiple iterations of hash algorithms (1000-10000 times)

###### Testing for Software Security
- Logging activity:
  - OS logs: monitor access and authentication
  - Application logs: track data access, invalid data entry
  - Ensure sensitive data is not included in logs, and logs are not unencrypted

###### What Do We Do as Developers?
- Continuously assess potential weaknesses in applications
- Limit access to sensitive data, especially admin accounts
- Ensure data protection through strong security measures

###### Performance Testing
- Evaluates system performance under load
  - Load testing: responsiveness with concurrent users
  - Stress testing: system behavior under overload
  - Breakpoint testing: finding the point at which the system breaks
