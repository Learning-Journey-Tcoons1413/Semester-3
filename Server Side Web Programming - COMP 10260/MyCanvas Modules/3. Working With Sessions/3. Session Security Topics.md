### **Session Security**

Sessions are too useful to be discarded without serious consequences. When we must avoid the standard mechanisms due to some requirement or business restriction we have to manage the sessions ourselves. [This Stack Overflow postLinks to an external site.](https://stackoverflow.com/questions/36753513/how-do-i-save-php-session-data-to-a-database-instead-of-in-the-file-system) touches on some of the reasons that this is a non-trivial exercise to do correctly.

Given that session are useful, we need to carefully protect our sessions through secure programming practices. There are other attacks that can compromise our website, such as someone getting shell access to the remote server and compromising the temporary directory where our session files are stored, that are beyond the scope of the course. This is why we try not to use a common shared temporary folder on a shared server. Most network administrators will be aware of this security risk and each user will have their own temporary directory assigned, or you can assign your own using the [session_save_path()Links to an external site.](https://www.php.net/manual/en/function.session-save-path.php) function.

Many people will argue that you should never store sensitive information directly in session variables because the files on the server are plain text - unencrypted text files are vulnerable to being read by anyone with access to them. Further if the session ID is compromised by some method, that data can be easily exposed. Even after changing the session save path from a shared folder into a folder within your file structure, anyone with access to your file structure can still read those files (including your host's employees). They can also read your source code and steal your database passwords. More control over your hosting environment means more responsibility on you to maintain it. For example an Azure instance can be encrypted so that you can only access it with the proper credentials, but then you must configure Linux, Apache, etc. yourself, or hire someone to do it for you.

Security and ease of use typically run in opposite directions and it is important to recognize that you need to strike a reasonable balance between these competing needs.

### **Session Expiration and Timeout**

- Set session expiration time with `session_set_cookie_params()` to control how long sessions are active.
- PHP has a default session timeout of 24 minutes. Adjust this using `session.gc_maxlifetime`.

### **Session Hijacking Prevention**

- Session hijacking is when an attacker steals a valid session ID to impersonate a user.
- Use cookie based sessions when possible to move the session id out of the URL.
- The attacker intercepts network traffic to capture session cookies. This can be done on unsecured Wi-Fi networks or compromised systems.
    - Use HTTPS to encrypt data during transmission, reducing the risk of session hijacking.
- Use secure session configuration settings, such as [`session.cookie_secure`Links to an external site.](https://www.php.net/manual/en/session.configuration.php#ini.session.cookie-secure), [session.use_strict_modeLinks to an external site.](https://www.php.net/manual/en/session.configuration.php#ini.session.use-strict-mode), and `[session.cookie_httponlyLinks to an external site.](https://www.php.net/manual/en/session.configuration.php#ini.session.cookie-httponly)` to mitigate the risks from XSS attacks.
- Regenerate session IDs periodically or after significant authentication events to prevent session fixation.

**Impact of Session Hijacking:**

- Once the attacker gains control of the user's session, they can:
    - Access the user's account, personal data, and sensitive information.
    - Perform actions on behalf of the user, such as making unauthorized transactions or altering account settings.

Don't rely on the IP address of the user when the session is started. This is an old fashioned idea - it relied on the underlying assumption that a user's IP address couldn't change during the session. This is not a valid assumption if your application wishes to remain mobile friendly - phones move from wifi to cellular networks and change access points. You can typically rely on the client's user agent being consistent during the session, however. Recording the user agent when initiating a session and validating it against `$_SERVER['HTTP_USER_AGENT']` during use could provide a hint that a session has been hijacked. Note that user agent strings can be set by a user and should be sanitized if the possibility of an injection attack exists.

### **Session Fixation Prevention**

- Session fixation occurs when an attacker sets a user's session ID, possibly enabling unauthorized access.  
    - The attacker tricks the user into using a specific session ID, often by sharing a malicious link or sending a phishing email.
    - The user unknowingly logs in using the attacker's session ID, enabling the attacker to gain control over the user's session.
- Use `session_regenerate_id()` to change the session ID after authentication.
- more at https://acrossecurity.com/papers/session_fixation.pdf

### **Session Handling Best Practices**

1. Only store necessary data in sessions.
2. Sanitize and validate user input before using it in session variables.
3. Regularly clean up expired sessions using session garbage collection settings/session_destroy().
4. Implement proper logout procedures to clear session data.
5. Monitor session activity for any irregularities.

Sessions are an essential tool for maintaining user state in web applications. By using secure session management techniques and understanding the potential risks, developers can ensure the integrity and privacy of user data during their interactions with the application. Proper session handling is crucial for building secure and user-friendly web applications. Session hijacking is a serious security threat that can compromise user accounts and expose sensitive data. By implementing strong security practices and staying vigilant against attacks, developers can significantly reduce the risk of session hijacking and protect both the application and its users.
